# Music recommendations on Yambda

This project contains experiments on music recommender systems built on the [Yambda](https://huggingface.co/datasets/yandex/yambda) dataset. It currently covers **candidate generation (retrieval)**, with two families of methods:

1. **Classic recommenders:** popularity, artist counters, item-to-item over three kinds of item similarity, and ALS.
2. **Two-tower neural retrieval:** one model trained with seven different objectives, from full softmax to in-batch sampled softmax with logQ correction.

Every method is evaluated the same way: top-100 recommendations, compared against the tracks each user liked in the following week.

Planned next: a ranking stage on top of these candidates, and sequential (Transformer) user encoders.

## Setup

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
./scripts/download_data.sh        # ~360 MB, see data/README.md
pytest                            # unit tests, no data needed
```

## Usage

```bash
python scripts/run_classic.py                     # all classic methods  -> results/classic.md
python scripts/run_classic.py --methods als cf-tfidf

python scripts/run_two_tower.py --loss inbatch-logq           # one objective -> results/two_tower.md
python scripts/run_two_tower.py --loss bpr --user-fraction 0.05   # quick smoke run on 5% of users
./scripts/run_all_two_tower.sh                                # every objective
```

The device is chosen automatically (CUDA, then Apple MPS, then CPU). Override it with `--device`.

## Data and evaluation protocol

* **Interactions:** likes from Yambda-500M, restricted to tracks that have a pretrained embedding and at least 5 likes. After filtering there are 7.76M train likes over 157K tracks and 81K users.
* **Split:** temporal. The last 7 days form the test set, which is restricted to users who appear in train (37.4K users, 254K likes). Models only ever see train.
* **Metrics @100:** each metric is averaged over test users, except Coverage.
  * **HitRate:** at least one test like appears in the top-100.
  * **Recall:** hits / min(#test likes, 100).
  * **nDCG:** with binary relevance.
  * **Coverage:** the share of the train catalog that appears in at least one user's top-100.
* **Filling short lists:** any list shorter than 100 is padded with the most popular tracks, so every method is compared on full lists.

| TopPop | 0.1124 | 0.0308 | 0.0111 | 0.0006 |
| Item2Item (content embeddings) | 0.1285 | 0.0307 | 0.0110 | 0.9136 |

How each method builds its candidates:

* **TopPop:** the 100 most-liked tracks in train, given to every user.
* **Favourite artists:** rank artists by how often the user liked them in their last 100 likes. Take each artist's 20 most popular tracks and drop the ones the user has already liked.
* **Item-to-item:** for each of the user's last *N* likes, take the item's nearest neighbours. Score each candidate by the sum of its similarities, weighted by time decay `2^{-(L-t)/τ}`, then remove tracks already in the user's history. The three variants differ only in where the similarity comes from:
  * **Content embeddings:** cosine similarity over the pretrained Yambda embeddings. Exact top-200 neighbours are computed in batches on the GPU.
  * **Item2Vec:** word2vec (CBOW) trained on chronological user sequences.
  * **Item-based CF:** cosine similarity over columns of the sparse user-item matrix, optionally TF-IDF weighted (`implicit`).
* **ALS:** implicit-feedback matrix factorisation with 128 factors and 30 iterations, using either raw or TF-IDF-weighted counts.

| BPR, uniform negatives | 0.2274 | 0.0631 | 0.0218 | 0.1412 |
| Sampled softmax, in-batch negatives | 0.2081 | 0.0564 | 0.0202 | 0.7265 |
| BCE, uniform negatives | 0.1955 | 0.0514 | 0.0178 | 0.2100 |

Coverage here is measured over the full 157,357-item catalog. On an Apple M-series GPU, one epoch takes about 2.5 minutes for the in-batch and BPR objectives, about 14 minutes with 2048 uniform negatives per user, and about 30 minutes for full softmax.

Model and training setup:

* **User tower:** the sum of the embeddings of the user's last 100 liked items (bag of items).
* **Item tower:** the same embedding table, so a score is `r(u, i) = <P_u, E_i>`.
* **Training:** next-item prediction. A history of length *T* yields *T − 1* (prefix → next item) samples. Each model is trained for 1 epoch with 64-dim embeddings, Adam at lr 1e-3, and batch size 2048 (256 for full softmax).
* **Batch format:** histories are stored flattened, as a concatenated id tensor plus per-user lengths, so there is no padding. The user tower is a single `index_add_`.
* **Inference:** brute-force scoring against the full catalog, then top-100.

The objectives (all in [`src/recsys/two_tower/models.py`](src/recsys/two_tower/models.py)):

| Objective | Negatives |
|---|---|
| Full softmax | the whole catalog |
| BCE | 2048 uniform per user, pointwise |
| BPR | 1 uniform per user, pairwise |
| Sampled softmax, uniform | 2048 uniform per user |
| Sampled softmax, in-batch | the other users' positives |
| In-batch + uniform | the other users' positives plus 2048 shared uniform items |
| In-batch + logQ | the other users' positives, with logits corrected by `− log q(i)` |

## Findings

**Overall.** The best two-tower model, in-batch softmax with logQ correction, beats the best classic model, ALS on TF-IDF, by about 11% in Recall@100 (0.108 vs 0.098). It also recommends 2.6× more of the catalog. The two-tower model gets there with a bag-of-items user tower and a single epoch of training.

**Classic recommenders**

* **Behaviour beats content.** Item-to-item over the pretrained content embeddings barely beats TopPop on accuracy, although it has the widest coverage. Two tracks that sound alike are often not liked by the same people. Similarities learned from behaviour, through Item2Vec or co-occurrence, are clearly better.
* **Favourite artists is a strong cheap baseline.** It scores Recall 0.064 with a few `group_by`s and no training. For music, artist loyalty is a very strong signal.
* **In item-based CF, TF-IDF helps through `sqrt`, not `idf`.** With TF-IDF, Recall rises by 50% (0.054 → 0.081). Cosine similarity normalises each item's column, so the per-item `idf` factor cancels out entirely. The gain comes from `sqrt(count)`: it damps repeated likes of the same track, and some pairs are repeated hundreds of times. Without damping, such a pair dominates an item's vector.
* **In ALS, both parts of TF-IDF matter.** There are no column norms in ALS, so `idf` lowers the confidence of likes on popular tracks. This improves Recall (0.081 → 0.098) and more than doubles coverage (0.07 → 0.17).
* **ALS beats item-to-item CF on accuracy but covers far less of the catalog.** ALS fits one global low-rank model on each user's entire history and can capture transitive similarity. Item-to-item only sums pairwise neighbours of recent likes. The cost of the low-rank model is that it concentrates on popular tracks.

**Two-tower objectives**

* **The choice of objective matters more than the architecture.** With the same model, Recall ranges from 0.051 to 0.108 depending on the loss alone.
* **Softmax-style losses beat BCE and BPR.** BCE scores each item independently. BPR only compares the positive with one random negative per step. Softmax losses make many items compete for the positive, which matches how the model is used at retrieval time, so they perform best.
* **Full softmax is not the winner here.** With one epoch at batch size 256 it falls slightly behind the sampled variants, and it is the slowest by far. Its cost grows linearly with the catalog size, which rules it out for catalogs of millions of tracks.
* **Pure in-batch negatives over-penalise popular tracks.** In-batch negatives are other users' positives, so a track is sampled as a negative in proportion to its popularity, and the model learns to push popular tracks down. Recommendations drift to the long tail: coverage reaches 0.73, but Recall drops to 0.056.
* **Two remedies for the in-batch bias:**
  * **Mixed negatives.** Adding uniform negatives to the in-batch ones partly fixes the bias (Recall 0.088).
  * **logQ correction.** Subtracting `log q(i)` removes the bias. It reaches the best Recall (0.108) and runs as cheaply as plain in-batch training.
* **logQ lowers coverage, and that is expected.** Coverage falls from 0.73 to 0.43 because popular tracks are no longer penalised unfairly, so they return to users' lists where they belong.
* **Next steps:**
  * a sequential user tower (Transformer or GRU) in place of the bag of items;
  * more than one epoch;
  * excluding already-liked tracks at inference;
  * masking in-batch "negatives" that are actually the same track as the positive.

## Project layout

```
src/recsys/
  data.py          loading, filtering, temporal split
  metrics.py       HitRate / Recall / nDCG / Coverage
  baselines.py     TopPop, favourite artists, popularity padding
  item2item.py     neighbour search (GPU cosine, word2vec, sparse CF) + time-decayed aggregation
  matrix.py        sparse user-item matrix, TF-IDF, ALS
  report.py        leaderboard CSV / Markdown
  two_tower/
    data.py        next-item dataset, flattened collate, padding helper
    models.py      user encoder, two-tower base, loss variants
    train.py       training loop and full-catalog evaluation
scripts/           entry points (benchmarks, data download)
tests/             unit tests for metrics, batching, encoder and losses
results/           generated leaderboards
```
