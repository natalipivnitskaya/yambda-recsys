# Music recommendations on Yambda

This project contains experiments on music recommender systems built on the [Yambda](https://huggingface.co/datasets/yandex/yambda) dataset. It covers both stages of a typical recommendation pipeline:

1. **Candidate generation (retrieval):** finding about 100 promising tracks out of 157K.
   * **Classic recommenders:** popularity, artist counters, item-to-item over three kinds of item similarity, and ALS.
   * **Two-tower neural retrieval:** one model trained with seven different objectives, from full softmax to in-batch sampled softmax with logQ correction.
   * **Sequential retrieval:** a GPT-style causal Transformer over the user's last 100 likes, trained on next-item prediction at every position.

   Evaluated with top-100 recommendations against the tracks each user liked in the following week.
2. **[Ranking](#ranking):** ordering the tracks a user is about to hear. A CatBoost baseline and neural rankers (DCN-v2 with a mixture of low-rank experts, single- and multi-task) predict full plays and likes from lagged counters, ids and artist/album lists. Evaluated by pairwise accuracy on neighbouring listens.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev,ranking]"     # "ranking" adds CatBoost
./scripts/download_data.sh          # retrieval data, ~360 MB (see data/README.md)
```

## Usage

```bash
python scripts/run_classic.py                     # all classic methods  -> results/classic.md
python scripts/run_classic.py --methods als cf-tfidf

python scripts/run_two_tower.py --loss inbatch-logq           # one objective -> results/two_tower.md
python scripts/run_two_tower.py --loss bpr --user-fraction 0.05   # quick smoke run on 5% of users
./scripts/run_all_two_tower.sh                                # every objective

python scripts/run_sequential.py                              # Transformer, 20 epochs -> results/sequential.md
python scripts/run_sequential.py --epochs 1 --user-fraction 0.05  # quick smoke run

python scripts/run_ranking.py                                 # all rankers -> results/ranking.md
python scripts/run_ranking.py --model dcn-mix-mt              # one model
python scripts/run_ranking.py --model mlp --train-fraction 0.02   # quick smoke run
```

The device is chosen automatically (CUDA, then Apple MPS, then CPU). Override it with `--device`.

## Retrieval

### Data and evaluation protocol

* **Interactions:** likes from Yambda-500M, restricted to tracks that have a pretrained embedding and at least 5 likes. After filtering there are 7.76M train likes over 157K tracks and 81K users.
* **Split:** temporal. The last 7 days form the test set, which is restricted to users who appear in train (37.4K users, 254K likes). Models only ever see train.
* **Metrics @100:** each metric is averaged over test users, except Coverage.
  * **HitRate:** at least one test like appears in the top-100.
  * **Recall:** hits / min(#test likes, 100).
  * **nDCG:** with binary relevance.
  * **Coverage:** the share of the train catalog that appears in at least one user's top-100.
* **Filling short lists:** any list shorter than 100 is padded with the most popular tracks, so every method is compared on full lists.

| Item2Item (content embeddings) | 0.1285 | 0.0307 | 0.0110 | 0.9136 |

How each method builds its candidates:

* **TopPop:** the 100 most-liked tracks in train, given to every user.
* **Favourite artists:** rank artists by how often the user liked them in their last 100 likes. Take each artist's 20 most popular tracks and drop the ones the user has already liked.
* **Item-to-item:** for each of the user's last *N* likes, take the item's nearest neighbours. Score each candidate by the sum of its similarities, weighted by time decay `2^{-(L-t)/τ}`, then remove tracks already in the user's history. The three variants differ only in where the similarity comes from:
  * **Content embeddings:** cosine similarity over the pretrained Yambda embeddings. Exact top-200 neighbours are computed in batches on the GPU.
  * **Item2Vec:** word2vec (CBOW) trained on chronological user sequences.
  * **Item-based CF:** cosine similarity over columns of the sparse user-item matrix, optionally TF-IDF weighted (`implicit`).
* **ALS:** implicit-feedback matrix factorisation with 128 factors and 30 iterations, using either raw or TF-IDF-weighted counts.

| BPR, uniform negatives | 0.2274 | 0.0631 | 0.0218 | 0.1412 |
| Sampled softmax, in-batch negatives | 0.2081 | 0.0564 | 0.0202 | 0.7265 |
| BCE, uniform negatives | 0.1955 | 0.0514 | 0.0178 | 0.2100 |

Coverage here is measured over the full 157,357-item catalog. On an Apple M-series GPU, one epoch takes about 2.5 minutes for the in-batch and BPR objectives, about 14 minutes with 2048 uniform negatives per user, and about 30 minutes for full softmax.

Model and training setup:

* **User tower:** the sum of the embeddings of the user's last 100 liked items (bag of items).
* **Item tower:** the same embedding table, so a score is `r(u, i) = <P_u, E_i>`.
* **Training:** next-item prediction. A history of length *T* yields *T − 1* (prefix → next item) samples. Each model is trained for 1 epoch with 64-dim embeddings, Adam at lr 1e-3, and batch size 2048 (256 for full softmax).
* **Batch format:** histories are stored flattened, as a concatenated id tensor plus per-user lengths, so there is no padding. The user tower is a single `index_add_`.
* **Inference:** brute-force scoring against the full catalog, then top-100.

The objectives (all in [`src/recsys/two_tower/models.py`](src/recsys/two_tower/models.py)):

| Objective | Negatives |
|---|---|
| Full softmax | the whole catalog |
| BCE | 2048 uniform per user, pointwise |
| BPR | 1 uniform per user, pairwise |
| Sampled softmax, uniform | 2048 uniform per user |
| Sampled softmax, in-batch | the other users' positives |
| In-batch + uniform | the other users' positives plus 2048 shared uniform items |
| In-batch + logQ | the other users' positives, with logits corrected by `− log q(i)` |

#### Sequential (Transformer) retrieval

<!-- generated by scripts/run_sequential.py: results/sequential.md -->
| Method | HitRate@100 | Recall@100 | nDCG@100 | Coverage@100 |
|---|---:|---:|---:|---:|
| Transformer (2 layers, d=64, len 100, 20 ep), in-batch negatives + logQ | 0.3532 | 0.1222 | 0.0458 | 0.3577 |
| Transformer (2 layers, d=64, len 100, 10 ep), in-batch negatives + logQ | 0.3225 | 0.1070 | 0.0384 | 0.2420 |
| Transformer (2 layers, d=64, len 100, 10 ep), in-batch negatives | 0.1071 | 0.0247 | 0.0076 | 0.3644 |

Training takes about 75 seconds per epoch on an Apple M-series GPU, plus a full-catalog evaluation after each epoch.

Model and training setup (in [`src/recsys/sequential/`](src/recsys/sequential/)):

* **User tower:** a GPT-style causal Transformer with item embeddings, learned position embeddings, and 2 pre-LayerNorm blocks (2 heads, GELU MLP, dropout 0.1). The state after event *t* attends only to events up to *t*.
* **Item tower:** the same item embedding table as the input, so a score is `r(u_t, i) = <h_t, E_i>`.
* **Training:** next-item prediction at every position at once. Each history is cut into non-overlapping windows of up to 100 steps, `history = [i_1 … i_L]` → `targets = [i_2 … i_{L+1}]`. A window costs one Transformer pass instead of *L* separate samples, and an epoch still uses each train like exactly once as a target. Batches hold 128 windows; Adam at lr 1e-3.
* **Loss:** sampled softmax at every position. For each batch, 512 negatives are drawn from the batch's own targets (so in proportion to popularity) and shared by all positions. `log q(i)` is subtracted from the positive and negative logits, and negatives that are the position's own positive are masked out.
* **Inference:** the hidden state after the last of the user's 100 most recent likes, scored against the full catalog.

### Findings

**Overall.** The causal Transformer is the best retrieval model so far: Recall@100 0.122 and nDCG@100 0.046. That is 13% and 16% above the best two-tower model, and 25% above ALS in Recall. Among the earlier models, the best two-tower model (in-batch softmax with logQ correction) beats the best classic model, ALS on TF-IDF, by about 11% in Recall@100 (0.108 vs 0.098). It also recommends 2.6× more of the catalog, using only a bag-of-items user tower and a single epoch of training.

**Classic recommenders**

* **Behaviour beats content.** Item-to-item over the pretrained content embeddings barely beats TopPop on accuracy, although it has the widest coverage. Two tracks that sound alike are often not liked by the same people. Similarities learned from behaviour, through Item2Vec or co-occurrence, are clearly better.
* **Favourite artists is a strong cheap baseline.** It scores Recall 0.064 with a few `group_by`s and no training. For music, artist loyalty is a very strong signal.
* **In item-based CF, TF-IDF helps through `sqrt`, not `idf`.** With TF-IDF, Recall rises by 50% (0.054 → 0.081). Cosine similarity normalises each item's column, so the per-item `idf` factor cancels out entirely. The gain comes from `sqrt(count)`: it damps repeated likes of the same track, and some pairs are repeated hundreds of times. Without damping, such a pair dominates an item's vector.
* **In ALS, both parts of TF-IDF matter.** There are no column norms in ALS, so `idf` lowers the confidence of likes on popular tracks. This improves Recall (0.081 → 0.098) and more than doubles coverage (0.07 → 0.17).
* **ALS beats item-to-item CF on accuracy but covers far less of the catalog.** ALS fits one global low-rank model on each user's entire history and can capture transitive similarity. Item-to-item only sums pairwise neighbours of recent likes. The cost of the low-rank model is that it concentrates on popular tracks.

**Two-tower objectives**

* **The choice of objective matters more than the architecture.** With the same model, Recall ranges from 0.051 to 0.108 depending on the loss alone.
* **Softmax-style losses beat BCE and BPR.** BCE scores each item independently. BPR only compares the positive with one random negative per step. Softmax losses make many items compete for the positive, which matches how the model is used at retrieval time, so they perform best.
* **Full softmax is not the winner here.** With one epoch at batch size 256 it falls slightly behind the sampled variants, and it is the slowest by far. Its cost grows linearly with the catalog size, which rules it out for catalogs of millions of tracks.
* **Pure in-batch negatives over-penalise popular tracks.** In-batch negatives are other users' positives, so a track is sampled as a negative in proportion to its popularity, and the model learns to push popular tracks down. Recommendations drift to the long tail: coverage reaches 0.73, but Recall drops to 0.056.
* **Two remedies for the in-batch bias:**
  * **Mixed negatives.** Adding uniform negatives to the in-batch ones partly fixes the bias (Recall 0.088).
  * **logQ correction.** Subtracting `log q(i)` removes the bias. It reaches the best Recall (0.108) and runs as cheaply as plain in-batch training.
* **logQ lowers coverage, and that is expected.** Coverage falls from 0.73 to 0.43 because popular tracks are no longer penalised unfairly, so they return to users' lists where they belong.
* **Next steps:**
  * more than one epoch;
  * excluding already-liked tracks at inference;
  * masking in-batch "negatives" that are actually the same track as the positive (done in the Transformer).

**Sequential user tower**

* **Order matters, but the gain needs many epochs.** The Transformer sees each train like as a target once per epoch, just like the two-tower model. Yet after one epoch it reaches only Recall 0.030, against 0.108 for the bag of items. It catches up around epoch 10 (0.107) and is still improving at epoch 20 (0.122). The comparison is therefore not compute-matched: the bag-of-items model was trained for one epoch only, and training it longer is the obvious control.
* **logQ correction is essential here.** Without it, the Transformer scores Recall 0.025 at epoch 10, below TopPop, against 0.107 with it. Coverage rises to 0.36: the model pushes popular tracks down, as in the two-tower case, but the damage is much larger (two-tower in-batch without logQ still scores 0.056).
* **Coverage grows with training.** With logQ, coverage rises steadily from 0.01 after epoch 1 to 0.36 after epoch 20. The model starts by recommending popular tracks and learns the long tail later.
* **Caveat:** the number of epochs was chosen by looking at test metrics, since there is no validation split yet. Two runs with the same setup differ by about 0.002 in Recall at epoch 10.
* **Next steps:**
  * a validation split, then longer training with a learning-rate schedule;
  * a compute-matched bag-of-items baseline (20 epochs);
  * excluding already-liked tracks at inference;
  * larger models and longer contexts.

## Ranking

The ranker orders tracks that are about to be played to a user. It predicts two targets for each listen: **full play** (at least 95% of the track played) and **like**.

### Data and evaluation protocol

* **Listens:** Yambda-50M listens from recommendation surfaces only: 22.5M listens by 8.8K users over 491K tracks. They come preprocessed as [`yambda-50m-lag-features`](https://huggingface.co/datasets/matfu21/yambda-50m-lag-features). Each like is attributed to the nearest listen of the same track within 24 hours.
* **Features:**
  * 15 counters: listens, likes, full plays, skips and average played ratio, each per user, per track and per user×track. Every counter is computed at `timestamp − 15 min`, so a listen never sees its own feedback or the feedback on its neighbours.
  * `uid` and `item_id`.
  * The track's lists of artists and albums.
* **Split:** temporal. The last 30 days form the test set.
* **Preference events:** both splits keep only listens whose `is_like` or `is_full_play` differs from the previous or next listen of the same user. Listens with the same feedback on both sides carry no ranking signal, and filtering them out provably leaves the metric unchanged (covered by a unit test). After filtering there are 5.95M train and 928K test listens. In test, 5.5% of these listens are liked and 50.5% are full plays.
* **Metric:** pairwise accuracy. Take every pair of neighbouring listens of the same user that are at most 15 minutes apart and have different labels. A pair is correct if the positive listen gets the higher score; ties count 0.5, so random scoring gets 0.5. It is computed separately for likes and for full plays.

### Results

<!-- generated by scripts/run_ranking.py: results/ranking.md -->
| Method | PairAcc (like) | PairAcc (full play) |
|---|---:|---:|
| DCN-v2 mixture, multi-task (per-task heads) | 0.5443 | 0.5967 |
| DCN-v2 mixture, multi-task (joint score) | 0.5388 | 0.4915 |
| Random | 0.4998 | 0.4999 |
| Popularity (train listens) | 0.4876 | 0.5247 |
| CatBoost (full play) | 0.4873 | 0.5884 |
| DCN-v2 + MLP | 0.4845 | 0.5980 |
| Concat + MLP | 0.4835 | 0.5969 |
| DCN-v2 (mixture of low-rank experts) + MLP | 0.4820 | 0.5979 |

Models trained on full plays only use the same score for both metrics. The multi-task model is shown two ways: with each head scoring its own target, and with a single joint score `log P(full play) + log P(like)` used for both targets.

The models:

* **CatBoost:** 500 trees of depth 8, trained on a 3M-row sample with `uid` and `item_id` as categorical features. Takes about 20 minutes on the CPU.
* **Neural rankers:** every model concatenates three feature encodings into a 280-dim vector, passes it through an optional cross network and then a 512-256 MLP, with one logit per task. Each takes 1.5–3 minutes per epoch on an Apple M-series GPU.
  * **Counters:** piecewise-linear encoding ([Gorishniy et al., 2022](https://arxiv.org/abs/2203.05556)). Each counter is split into up to 32 quantile bins and encoded as how far its value has filled each bin, then mapped to 8 dimensions per feature.
  * **Ids and id lists:** multihash unified embeddings ([Coleman et al., 2023](https://arxiv.org/abs/2305.12102)). There is one shared table of 2²⁰ × 16. Each feature is looked up with its own hash functions (4 for tracks, 2 each for users, artists and albums), and the vectors are concatenated. Artist and album lists are mean-pooled.
  * **Cross network:** three DCN-v2 layers ([Wang et al., 2021](https://arxiv.org/abs/2008.13535)), `x_{l+1} = x_l + x0 ⊙ (U Vᵀ x_l + b)` with rank 64. The "mixture" variant uses 4 low-rank experts per layer with a softmax gate.
  * **Training:** BCE summed over tasks, AdamW at lr 2e-3 with a one-cycle schedule, batch size 4096, **1 epoch**.

### Findings

* **Full play is not a proxy for like.** Every model trained only on full plays scores *below random* on likes (about 0.485), and so do CatBoost and popularity. Within neighbouring pairs, the liked listen is slightly more often the one predicted *less* likely to be played to the end. Likes need their own training signal.
* **A multi-task model serves both targets.** With a like head next to the full-play head, the shared model reaches 0.544 on likes and keeps full-play accuracy at 0.597, matching the single-task models.
* **Naively combining the heads fails.** In the joint score `log P(like) + log P(full play)`, the like term varies far more (likes are rare, so its log-probabilities spread widely) and dominates the sum. Full-play accuracy drops back to 0.49. Combining the heads needs tuned weights, or rank-based fusion.
* **Neural rankers beat CatBoost on full plays** (0.598 vs 0.588), and they train faster here, although CatBoost runs on the CPU and only sees a sample.
* **Feature crosses add little here.** Concat+MLP, DCN-v2 and the mixture of experts all land within 0.001 of each other. With counters this informative, the MLP already captures most of the interactions.
* **One epoch is better than two.** All neural models lose about 0.017 full-play accuracy in a second epoch while training loss keeps falling. This is the *one-epoch overfitting* typical of CTR models with large id-embedding tables ([Zhang et al., 2022](https://arxiv.org/abs/2209.06053)). This was observed on the test metric; the setup has no separate validation split yet, and adding one is the first next step.
* **Next steps:**
  * a validation split for choosing the number of epochs and the head-combination weights;
  * sequence features from the user's recent listens;
  * reranking the retrieval candidates from the first part of the project.
